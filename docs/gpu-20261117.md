# 在现有环境启用 GPU（2026-11-17）

使用原来的 `.venv`，没有新增 Python 环境或 GPU 通信服务。
长期模块的文本嵌入和重排、Mem0 原生 HuggingFace 嵌入使用 CUDA；
两库继续独立存储、并行检索，向量库过滤与合并仍由 CPU 完成。
正常查询直接使用 GPU FP32 模型，不逐次调用 CPU 模型复核排序。

## 环境

- Python：既有 Windows x64 / 3.14.7。
- 显卡：RTX 5060 Laptop GPU，8151 MiB 显存；已有驱动 617.14。
- 项目 `.venv` 新装 `torch==2.14.0+cu130`、`torchvision==0.29.1+cu130`，CUDA runtime 13.0。
- CUDA 可用性、sm_120 支持、显卡矩阵运算及 torchvision NMS 实测通过。
- 基础 Miniconda 的 CPU 包没有被卸载；GPU 包安装在项目 `.venv/Lib/site-packages`，通过环境优先级使用。
- 没有安装新显卡驱动，也没有另建系统 CUDA 开发环境。

安装清单位于 `requirements-gpu.txt`，来源为 PyTorch 官方 CUDA 13.0 wheel 仓库。
依赖变更前后的清单与 pip 计划保存在 `runs/gpu-20261117/`。
安装没有新增 pip 依赖冲突；检查中既有 Mem0/protobuf 版本约束提示保持原样，本轮未改动该基础包。

## 为什么 CPU、GPU 曾出现排序不同

原来的 CPU 重排使用官方 INT8 ONNX 量化权重；GPU 使用同一模型的原始 FP32 权重。
该对照同时改变了计算精度与设备，不能把排序变化直接归因于显卡。
例如“光影包”问题，FP32 对两个低位候选的分差仅约 0.0165，量化后次序发生交换。
GPU 不会修改保存的经历，变化发生在检索候选打分与交付排序。

随后补做同精度对照：CPU、GPU 都用原始 FP32 模型，候选、模型、token 上限与输出预算一致。
16 个真实问题/改写问法，每题两边各 2 次，共 64 次调用，结果为：

- 16 个问法的重排输入指纹一致，最终交付文本、来源、顺序与表示层级一致。
- 模型打分最大绝对差约 `0.00001705`，没有改变这批问题的排序。
- CPU FP32 中位 736.913 ms，GPU FP32 中位 482.980 ms；95 分位为 953.353 → 647.867 ms。
- 铁屑问题中位约 983 → 474 ms；并行 JEV 问题约 887 → 479 ms。
- 两组严格指定来源命中均为 15/16；已知的“转录文件”改写仍命中另一条真实指令，未算作指定来源命中。

证据：`runs/gpu-20261117/same-precision/comparison.json`。

## 与此前 CPU 量化版的对照

另有同数据 CPU INT8 / GPU FP32 配对测试：16 个问法、每边各 5 次，共 160 次调用。
CPU 中位 659.164 ms，GPU 中位 295.671 ms；95 分位 913.991 → 455.676 ms。
两轮测试时机器状态不同，只比较各轮内部前后结果，不能混用成保证的固定延迟。
GPU 在两轮测得的总体中位约为 0.30–0.48 秒。

原 10 个真实问题，两组均 10/10 来源命中、指定原话全部覆盖；指定证据的排名也保持一致。
其中两个先前漏召回问题仍正常返回原始用户要求。
但 8 个问法的低位交付材料与 INT8 版有变化，不能宣称整个列表与旧版完全一致。
“光影包”问题低位出现无关画面描述，这也是 CPU FP32 的结果，属于后续需要改善的相关性问题，
并未通过“同精度一致”宣称它已经解决。本文只评价检索证据，不声称最终模型回答准确率。

证据：`runs/gpu-20261117/paired/comparison.json`。

曾试验在分差接近时调用 CPU INT8 复核，可恢复旧列表，但 16 题中有 10 题触发复核，削弱提速收益。
按用户随后确认的方向，最终采用直接 GPU FP32。该复核逻辑已从生产代码删除，
仅在测试程序内保留实验复现能力，不属于正常运行路径。

## 写入、重试与兼容

从同一真实经历快照抽取 25 条，使用原生 Mem0 GPU 子进程写入一个新的隔离库，并完整重复投递。
随后关闭 GPU 子进程，用 CPU 模型重开该库：仍为 25 条，原文、segment_id 和 source_ids 全部保留，
检索通过。这验证了设备切换不需要重建数据库，也没有通过重复写入改变事实。
设备参数只作为模型运行配置，不加入已有 Mem0 嵌入模型身份指纹。

证据：`runs/gpu-20261117/io-validation/result.json`。

## 配置、复测与回退

JShi 仍由既有 `.venv/Scripts/python.exe` 启动。`dual` 模块使用：

```dotenv
REMS_EMBEDDING__DEVICE=cuda
REMS_RECALL_RERANK_DEVICE=cuda
REMS_RECALL_RERANK_ONNX_FILE=
```

最后一项为空表示使用 PyTorch 原始权重；CUDA 配置不会静默加载 CPU ONNX 模型。
`/status` 的 memory 信息可核对设备设置与 Mem0 子进程实际返回的 `cuda:0`。
没有减少候选数量、缩短 512 token 上限或最终材料预算，也没有加超时截断。

从本项目执行：

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-gpu.txt
.\.venv\Scripts\python.exe scripts/setup_recall_models.py --gpu
.\.venv\Scripts\python.exe scripts/compare_gpu_recall.py --audit runs/cutover-audit-20261117-v2 --cases runs/recall-fix-20261117/acceptance-cases.json --out runs/gpu-new-compare --repeats 5 --paraphrases
.\.venv\Scripts\python.exe scripts/compare_gpu_recall.py --audit runs/cutover-audit-20261117-v2 --cases runs/recall-fix-20261117/acceptance-cases.json --out runs/gpu-new-fp32 --repeats 2 --paraphrases --cpu-fp32
```

测试必须使用关闭的隔离快照和新输出目录。脚本会复制测试库，不打开正式 Qdrant；完成后关闭所有测试子进程。
真实内容与报告只保存在被 Git 忽略的 `runs/`。

若需回到此前 CPU 量化版，在 JShi 模块配置中把两个 device 设为 `cpu`，
把 `REMS_RECALL_RERANK_ONNX_FILE` 恢复为 `onnx/model_quint8_avx2.onnx`，正常退出并重启即可。
GPU 版 PyTorch 同样能执行 CPU 计算，不需要为了回退再次安装环境或迁移数据。
如需恢复安装前的包布局，先核实卸载目标位于项目 `.venv`；只移除本次安装的本地 torch/torchvision，
基础 Miniconda 的 CPU 包仍在，环境变更前清单可用于核对。不要操作全局解释器。

本轮仍是约 66 MB 近期库的测试，没有宣称完成 10 GB 规模验证；一年、10 GB、8 GB 清到 7 GB 的策略不变。
