# 双库并行检索的第二轮耗时优化（2026-11-17）

本轮保留已经修复漏召回的版本作为基线，专门优化仍需一秒多的查询。
采用相同真实数据、相同候选、模型、输入长度和最终预算，调整长期重排模型的 CPU 计算线程数。
两库仍同时检索，并等待两边完成后合并。Mem0 的原生检索、过滤和存储没有修改。

## 慢在哪里

先用独立快照拆分计时。长期库共 1,335 个事件、2,423 个向量点；近期库共 10,013 条原生 Mem0 记录。
初始三次热查询的中位数：铁屑问题总耗时约 1198 ms，其中长期重排约 934 ms；
并行 JEV 问题总耗时约 1211 ms，其中长期重排约 922 ms。两题的 Mem0 分支约 493–498 ms，
与长期分支重叠运行，不是串行相加。查询嵌入约 27–29 ms，长期向量候选查询约 78–79 ms；
最后合并、回忆轨迹写入及线程收尾只有几毫秒量级。

Mem0 的内部剖析表明，主要时间花在 Qdrant 本地模式对 10,013 条记录进行主体、代理和时间过滤。
剖析器会增加开销，因此只用它定位调用，性能结论采用关闭剖析器的独立计时。

长期重排模型默认每次把 6 条候选放在一个批次内，使用 4 个 ONNX 计算线程。
实际输入并不短：铁屑问题 6 条的有效 token 长度为 373、351、371、109、336、264；
并行 JEV 问题为 212、384、87、183、95、96。

## 采用与未采用的改动

增加 `REMS_RECALL_RERANK_THREADS` 参数，只控制 ONNX session 的 `intra_op_num_threads`。
通用默认仍是 4；本机有 14 个物理核、20 个逻辑处理器，经实测在 JShi 的 `dual` 配置中使用 8。
保持单批输入、512 token 上限、100 条候选池、6 条重排候选、模型权重及所有过滤规则不变。
这项设置不增加模型调用，不缓存问题答案，也不截断或提前结束任何一边的检索。
另外在 JShi `/status` 的 memory 信息中显示 `rerank_threads`，便于核实生效值。

未采用的实验：

- 按长度拆分重排批次：确实减少补齐开销，但量化模型的个别低位候选排序发生变化，未进入正式实现。
- 单线程重排：三条探针问题约 2.85–3.23 秒，明显更慢。
- 未修改 Mem0 包、Qdrant 包，也未改变 GC 策略或部署额外向量服务。

8 线程不是所有机器的通用最优值。它会增加 CPU 竞争，部分 Mem0 分支从约 0.5 秒变为约 0.65 秒；
本机的长期分支仍是关键路径，整体收益经下面的并行对照确认。

## 质量约束

自动验收同时检查来源命中、原话覆盖、交付材料、候选输入指纹、重排分数和分支错误：

- 原 10 题：两组均 10/10 来源命中，每次指定原话覆盖率均为 100%。
- 全部 16 个问法：前后每次交付的文本、来源、顺序、事件/对象身份及表示层级完全一致。
- 重排输入指纹一致，模型分数最大差值为 0；所有分支错误为空。
- 包含改写问题的严格指定来源命中均为 15/16。仍是此前的“转录文件”改写命中另一条真实用户指令，
  没有因本轮提速新增漏召回，也没有把它统计成指定来源命中。

这些结论限于本次实际样本，衡量检索证据一致性，不冒充最终回答准确率或所有未来问题的保证。

## 为什么还有偶发的一秒多

后续只对两条重点问题各连续运行 8 次，记录 Python GC 回调：
并行 JEV 有一次总耗时约 1219 ms，其中第二代 GC 占约 295 ms（回收 190 个对象）；
该题其他次数约 893–954 ms。铁屑问题这轮约 839–876 ms，没有超过 10 ms 的 GC 停顿。
证据在 `runs/latency-20261117/gc-profile/timings.json`。

这定位到一种尾部延迟来源，不能据此把所有慢请求都归因于 GC。
本轮没有关闭自动回收、冻结整个 JShi 对象图或用超时丢弃记忆结果。
后续若继续处理尾部，应另测对象分配、GC 与长期内存增长，并继续使用相同的质量门槛。

## 复测与运行配置

```powershell
python scripts/profile_parallel_recall.py --audit runs/cutover-audit-20261117-v2 --cases runs/recall-fix-20261117/acceptance-cases.json --out runs/latency-new-profile --threads 8 --repeats 5

```

输出目录必须是新目录。输入是已关闭的隔离快照，两脚本会复制测试库，不接触正式 Qdrant；
结束时关闭两库及测试子进程。`--profile` 用于内部剖析，不能把其带开销的时间当作正式性能结果。
`scripts/benchmark_ranker_batches.py` 可独立复测已捕获的真实候选，输出每个实验的分数与排序。
这些文件含真实内容，放在被 Git 忽略的 `runs/` 中。

本轮回归：记忆模块单元及 JShi 契约测试 348 passed、1 skipped；
JShi 模块选择、台账、记忆控制与适配器测试 58 passed、1 skipped。
正式设置存于 JShi `.jshi/memory-modules.json` 的 `dual.settings.REMS_RECALL_RERANK_THREADS=8`。
本轮没有迁移、复制或覆盖正式两库，也没有修改 legacy 模块设置。
应用后 `/status` 确认 `module=dual`、`rerank_threads=8`、`recent_process=true`，
两库路径与应用前一致。旧实例进程族已退出，测试进程均退出，8 个测试向量目录的锁均已释放。
仅保留正式 JShi 与其 Mem0 子进程。激活记录在 `runs/latency-20261117/activation/result.json`。
