## 恢复的行为

| 配置 | 本副本默认值 | 实际含义 |
|---|---|---|
| `memory_refinement.enabled` | `false` | 使用完整事件封存；关闭默认轻量小事件及定龄提炼 |
| `event_min_chars` | `2000` | 正常事件下限，短内容留在缓冲 |
| `event_len_factor` | `1.5` | 正常事件上界为 3000，现有约定为严格小于上界 |
| `summary_l1_retention_ratio` | `1/3`（保留） | 封存时生成 L1，后续层级遵守原有预算与熔断 |
| `recall_event_index_level` | `L1` | 双库接入后以长期摘要索引为主；保留 L0 原文与词面回查 |

正常事件是语义事件，不是每凑够固定字数就盲目切块。不相关事项不应仅为凑字数而合并。
闲置、显式强制保存及超长拆分允许短于 2000 字的例外；短残余不会直接丢弃。
默认闲置规则仍为超过 `unclosed_char_limit * 0.5`（默认 1000 字）且闲置 3 天，或闲置 7 天。
封存立即生成摘要、角色、对象事实、情绪，保留 L0；新事件 `memory_stage=None`。
`refine_memory()` 在默认配置下不进行定龄提炼。

原来的历史默认值并非始终为两三千字：`84dd6e3` 将封存下限从 200 改为 900，
小事件改版前 `f0cb60c` 仍为 900、上限倍数为 2。上下文导出的 `len_msg` 约 2000，
JShi 的默认批量投递阈值 3000 又属于另一层。本次按用户明确要求设置 2000–3000 的事件范围，
不是宣称逐字恢复某个历史配置。

后续补接：长事件的边界模型读取分钟级来源时间，未知时间显式标记，不补写成当前时间；

这是新写入行为，未回填旧事件或重建旧索引。

## 双库接入（已实现）

接入 Mem0 OSS 2.2.1 原生原文写入、嵌入、Qdrant、检索和删除，两个模块并行写入与查询，
最后合并去重。近期库 365 天、10 GB 预算，8 GB 触发分批淘汰到 7 GB；
清理包含 Mem0 操作历史和 SQLite 空间回收。长期默认已切换 L1，保留 L0 回查。
具体边界、失败重试、预算限制和实际内容评测程序见[双库运行说明](dual-memory.md)。
L1 不保证比 L0 召回更好；本次用实际经历做三组对照，不把设计假设当质量结论。

## JShi 接口与使用

Python 包仍为 `rems`，`MemoryBackendPort`、`REMSPipeline.ingest_batch/recall`、
写入回执 `stored_marks`、历史对话人和对象字段及 HTTP 路由保持兼容。
相邻 `JShi/src` 的真实端口与适配代码已用于离线契约检查。

运行本副本时，在独立 Python 环境中从当前目录执行 `python -m pip install -e .`，
按 `.env.example` 提供所需模型配置，使用独立存储路径。
若从 JShi 启动，确保该进程实际导入本副本的 `rems`，并使用 `JSHI_MEMORY_BACKEND=rems3`。
可以通过 `python -c "import rems; print(rems.__file__)"` 核实导入位置。
已有环境变量和运行目录 `.env` 会覆盖默认值，尤其检查以下三个设置：

```dotenv
REMS_MEMORY_REFINEMENT__ENABLED=false
REMS_EVENT_MIN_CHARS=2000
REMS_EVENT_LEN_FACTOR=1.5
```

本次没有切换正在运行的 JShi，也没有迁移、重新切分或改写旧数据库中的小事件。
旧的隐藏/提炼节点仍按其原有来源关系读取，不会因默认开关改变而自动还原。
