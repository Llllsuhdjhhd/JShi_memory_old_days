## 全量隔离演练结果

Mem0 原生存储最终写入 10013 条，逐段核对 segment_id 缺项 0，目录约 66.22 MB。
长期索引重建约 135 秒；近期补导累计约 933 秒（含前半段旧逐条查重、后半段批量查重，
中途在已保存的 4500 条进度处正常中断测试、确认锁释放后恢复）。这是混合实现的一次演练耗时，
不能把它当成优化后从空库完整导入的基准。全过程未调用 LLM，也没有重生成长期事件。

1335 条事件的 ID、原文、摘要、来源元数据以及 7655 条写入回执，
与重建前的独立快照逐项汇总哈希一致。改变的是派生索引和独立近期库。
旧事件格式兼容，不能等同于旧小事件已变成长事件。

在同一个 10013 条 Mem0 库上，抽取分布于历史中的 25 个真实片段 ID，
逐条原生 get_all 用时 11388 ms，批量原生 get_all 用时 524 ms，返回 ID/正文完全相同。
这是查重子步骤的一次配对比较，不是端到端吞吐提升比例。
同一批记录转成 JShi 实时使用的本地无时区时间后重试，Mem0 的记录 ID 集合不变。

## 当前直接切换的障碍

1. `JShi/src/jshi/memory/rems3.py` 的 `neighbor_rems_src()` 固定优先使用相邻 `JShi_memory/src`。
   仅 `pip install -e JShi_memory_old_days` 不能保证切换，必须明确改变或配置加载来源，并核实实际 `rems.__file__`。
2. 当前 JShi 进程使用 `C:/Users/Lenovo/miniconda3/python.exe`；该环境尚无 Mem0。
   本项目 `.venv` 通过测试，不等于正在运行的 JShi 环境已经准备好。
3. 正式 Qdrant 的非阻塞锁探测显示正在使用中。不能原地重建或同时打开第二个客户端。
4. JShi 的记忆消费游标为 10244，既有经历不会自动再次投递。Mem0 要单独补历史，再接新批次；
   不要清零游标对两个库一起重放。回执未覆盖某段也不等于该段必然丢失，未闭合缓冲和旧回执策略需一并考虑。
5. JShi `.env` 使用 `REMS_CONTEXT_WINDOW=1000000`；早期实验源 `.env` 为 32768；
   当前模块默认 88000。事件下限与缓冲窗口是不同参数，正式切换前必须明确有效配置，
   不能用默认值实验冒充现网窗口下的长事件写入验收。
6. JShi 已有嵌入预热逻辑只处理长期嵌入器；需补 Mem0 预热和统一 `pipeline.close()` 生命周期接入。
   记忆后台清理线程及近期 Qdrant 的生命周期不能只依赖进程退出。

## 从真实数据发现并修正的问题

- 补上旧无 L1 事件的原文语义索引，保持旧数据可查，并且允许后续有摘要后切回 L1。
- 旧采样器把所有 subject 记录归 internal，而 JShi 正式规则只把 OutputKind.INTERNAL 归 internal；
  全台账中有 6188 条差异。现在直接调用正式转换函数，不维护另一套猜测规则。
- 旧采样器只取 actor_object_id，丢失回复段的对话对象推断；全台账发现 5382 条差异。
- 旧采样器没有补说话人或动作文本；全台账中 7758 条有差异。
- 台账含 207 条 planned_audio；正式转换会排除未播出的计划语音文字（若另有真实动作，仍可保留动作）。
  现在评测也遵守该规则，不把“准备说”当“已经说”。
- 历史回放使用 UTC aware 时间，JShi 实时适配会改成 local naive 时间；
  Mem0 幂等判断改为优先使用稳定 segment_id，避免同一片段在切换后重试被重复保存。
  同 ID 原文发生变化时明确报错，不能默默覆盖不可变经历。
- 现有 JShi 的同步/异步投递流程忽略返回结果中的 errors，若仅清空回执仍会推进游标。
  当前模块双库故障已改为抛出 MemoryIngestError，使 JShi 使用原有失败重试路径；
  使用实际 InProcessMemoryControl 验证故障时游标不动，重试成功后推进且长期事件不重复。
  空占位段正常跳过，已封存但失败的索引在重试确认前补建。
- 真实历史补导显示逐条调用 Mem0 get_all 查重会重复扫描本地库；适配层现按批次的片段 ID
  调用一次原生 get_all，分组上限 256，不改 Mem0 存储或检索算法。仍需用相同实际数据计时验证收益。

因此，2026-11-16 的 6 题分数只能保留为早期实验结果，不能作为本次切换验收。
